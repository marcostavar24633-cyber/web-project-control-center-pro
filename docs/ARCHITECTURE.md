# Архитектура WEB PROJECT CONTROL CENTER PRO 2.0

## 1. Общая схема

Платформа строится как модульный backend с отдельным frontend и независимыми worker-процессами.

```text
Browser
  |
  v
Web UI (React)
  |
  v
API (NestJS) ------ PostgreSQL
  |                     |
  |                     +-- Projects, users, settings, audits, reports
  |
  +------ Redis Queue
              |
              v
         Worker Pool
          |   |   |
          |   |   +-- Browser QA (Playwright)
          |   +------ SEO / Performance / Security checks
          +---------- Integrations / scheduled jobs
              |
              v
       Object Storage
       screenshots, traces, reports
```

## 2. Компоненты

### Web UI
- Dashboard и список проектов.
- Карточка проекта с URL, платформой, репозиторием и статусом.
- История проверок и детальные отчёты.
- Очередь задач и журнал операций.
- Просмотр предлагаемых изменений и diff.
- Управление интеграциями и политиками доступа.

Frontend не получает секреты интеграций и не выполняет произвольное сканирование от имени пользователя.

### API
- Аутентификация и авторизация.
- CRUD проектов и настроек.
- Создание заданий аудита.
- Проверка прав на запуск операций.
- Управление интеграциями и secret references.
- Выдача отчётов и ссылок на артефакты.
- Аудит действий пользователей и системных операций.

### Worker
- Выполнение длительных проверок.
- Ограничение времени, памяти и количества параллельных задач.
- Повтор задач с backoff и dead-letter queue.
- Генерация отчётов и скриншотов.
- Изоляция браузерных задач.
- Отправка статусов и метрик в API.

### PostgreSQL
Основное хранилище структурированных данных: проекты, настройки, задания, результаты, интеграции, пользователи, роли и журнал аудита.

### Redis
Очереди, блокировки, краткоживущие состояния и rate limiting. Redis не является основным хранилищем результатов.

### Object Storage
Скриншоты, Playwright traces, большие отчёты и прочие бинарные артефакты. Локальная папка worker допустима только для разработки.

## 3. Доменные сущности

- User
- Organization / Workspace
- Membership / Role
- Project
- ProjectEnvironment
- Integration
- SecretReference
- AuditRun
- AuditCheck
- AuditFinding
- Report
- Artifact
- FixProposal
- FixExecution
- Release
- Workflow
- WorkflowExecution
- Event / AuditLog

У каждой сущности должны быть стабильный ID, timestamps и явные правила доступа. Все данные проектов изолируются по workspace/project.

## 4. Жизненный цикл аудита

1. Пользователь выбирает проект и набор проверок.
2. API проверяет доступ, настройки и лимиты.
3. API создаёт AuditRun и ставит задание в очередь.
4. Worker получает задание и выполняет проверки в изолированной среде.
5. Результаты сохраняются как AuditCheck и AuditFinding.
6. Артефакты сохраняются в object storage.
7. API обновляет статус и уведомляет интерфейс.
8. Отчёт доступен в истории проекта.

Статусы: queued, running, completed, failed, cancelled.

## 5. Auto Fix — безопасный жизненный цикл

1. Анализ проблемы.
2. Создание FixProposal.
3. Генерация patch/diff в отдельной ветке.
4. Статический анализ и тесты.
5. Preview и визуальная проверка, если применимо.
6. Пользовательское подтверждение согласно policy.
7. Pull request или контролируемое применение изменений.
8. Повторные проверки.
9. Release либо rollback.

AI-предложение не считается исправлением, пока оно не прошло проверки.

## 6. Интеграции

Каждая интеграция реализуется через адаптер с:
- явными scopes/permissions;
- хранением credentials вне базы открытым текстом;
- проверкой срока действия и возможностью отзыва;
- журналом использования;
- таймаутами, retry и rate limits.

Первый приоритет: GitHub и Cloudflare Pages. Аналитические платформы подключаются после базовой модели проектов и безопасного хранения секретов.

## 7. Развёртывание

Frontend можно публиковать отдельно. API, worker, PostgreSQL, Redis и object storage должны быть доступны постоянно. Статический хостинг frontend сам по себе не запускает фоновые задачи и не заменяет backend runtime.
